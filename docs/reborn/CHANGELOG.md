# Changelog (Nexus Reborn)

Newest first. "Live" means running on our test server.

## 2026-11-13

- **A rejected player save no longer loses the whole save, and keybindings stop re-inserting themselves** (server): every game object clears its dirty flags while the save builds its change set, before the database commits it, so when the commit failed the objects believed they were clean and every change in that save was gone for good. One bad row (a duplicate INSERT, an UPDATE or DELETE that affected 0 rows, a foreign key) rolled back all of it, which is how the Soldier path and quest objective faults (01fc448d, 27658b2f) also cost quests, items and XP. Player saves (account and character, the periodic save, logout and the stop-time `SaveDirect`) now go through `SavePartial`: when the database rejects the change set, the already built rows are committed again one by one (up to four passes, so a row whose parent comes later still lands), every row the database accepts is saved, and only the rejected rows are dropped, each logged with its table, key and the database error, plus a "recovered after a rejection: N of M rows committed" warning. A DELETE of a row that is already gone counts as done. Restoring the dirty flags instead would have meant touching some 60 Save methods, and a rejected row would then be retried and rejected on every later save, failing all of them. Transient errors were and are retried by EF's retry strategy (5 times). Checked in throwaway containers against MySQL 8.0 with a change set holding a duplicate keybinding INSERT, an UPDATE of a missing title, a DELETE of a missing quest, a quest objective tracked before its new quest and three good rows: the location update, the new quest, its objective and the new title were saved, the two bad rows were dropped and logged. Separately, `Keybinding.Save` never cleared its Create flag (or Delete), so a keybinding a client uploaded was INSERTed again on every save that touched its set, failing the save as a duplicate, and when a later upload left it out it was only dropped from memory, never deleted. It now clears all of its flags like the other models (character and account keybindings). Character create, rename and delete and the guild and residence saves keep the all or nothing `Save`. `PartialSave.cs`, `CharacterDatabase.cs`, `AuthDatabase.cs`, `Player.cs`, `Keybinding.cs`.
- **Holdout bosses raised to Prime hit like a Superior again** (server, runs 20261112-210445 and 20261113-111922): Algoroc Soldier holdout Mechanical Hostiles (M314) passed five runs on 2026-11-03/04 with a Superior boss and died in wave 4 on every run since bosses became Prime (bc922b33): Prime multiplies the damage ratings by 2.65 instead of 1.75, on top of Prime health, and a level 12 boss with 9,551 health plus two regulars wore a level 18 soldier (9,180 health) down to death. A raised boss now keeps Prime rank, Prime health (still fitted to the time left, bac6d210) and the 1.5 scale, but its assault and support ratings (what spell damage scales by) are Superior's, or its own rank's where those are higher. Not a spell fault: the bot's second and third abilities cast 23 and 209 times that run; the PrereqCasterCast and SpellCooldown lines were early retries.
- **Drop hunts farm the best drop rate first** (bot, run 20261113-055005-zone13): Carcass Discovery (4539) spent 45 of 55 kills on the 1.5-6.8 % Grimstone creatures (28 on the 1.5 % one) and never saw the datapad that the Enraged Grimstone Mangler drops at 20 %, because after its five spawns the hunt fell back to all 47 cave spawns for the rest of the budget. - **Every server assigned key is now never generated, closing the save bug class behind the Soldier path and quest objective failures** (server, follow up to 01fc448d and 27658b2f): those two fixes were single cases of one mapping fault. A primary key column the server fills in itself, given `HasDefaultValue(0)` without `ValueGeneratedNever`, is treated by EF as store generated. At its CLR default (0, or an empty string) `Attach` then tracks an existing row as Added (a duplicate INSERT) and `Add` hands out a temporary key from one shared counter that can collide with a real row, and either way the whole save rolls back. All contexts were checked against their model snapshots and migrations. 130 key columns had the fault and none of them is AUTO_INCREMENT in any migration, so all are now `ValueGeneratedNever` and the snapshots match (no schema change, no migration). CharacterContext, 71: the `Id` of character, item, guild, guild_guild_data, residence, character_mail, character_bind, chat_channel and of every character_*, guild_*, residence_* and chat_channel_member child table, plus the second key parts achievementId, ampId, appearance slot, articleId, currencyId, customisation label, entitlementId, missionId, pet customisation type and objectId, petFlairId, questId (quest and objective), factionId, rewardTrackId, spell4BaseId, title, materialId, tradeskillId, schematicId, zoneMap and hexGroup, chat and guild member characterId, decorId, and character_create race, faction and creationStart. AuthContext, 20: the account id of every account_* child table with its second part (itemId, currencyId, entitlementId, entry, inputActionId, permissionId, roleId), account_daily_login.id, account_suspension.id, permission.id, role.id and role_permission id and permissionId. WorldContext, 39: disable, entity, entity_emote, entity_event, entity_loot, entity_property, entity_script, entity_spline, entity_stats, entity_vendor, entity_vendor_category, entity_vendor_item, item_loot, loot_group, loot_item, store_category, store_offer_group, store_offer_group_category, store_offer_item, store_offer_item_data, store_offer_item_price and tutorial key parts. Left generated on purpose: the real AUTO_INCREMENT keys (account.id, account_suspension.banId, server.id, chat_channel.chatId, group.groupId, the Friendship account and friendship ids) and the Guid `internal_message.id` keys, which EF fills in on the client. Chat, Friendship, Group and Query had nothing else to change. Inserts write the same rows as before (the column default was 0 anyway), only Attach and Add of a key at 0 behave differently. Checked in a throwaway SDK container: WorldServer Release builds with 0 errors, and `HasPendingModelChanges()` is false for all seven contexts on MySQL 8.0 and MariaDB 10.11 (a deliberately altered snapshot column did report pending, so the check works). `AuthContext.cs`, `CharacterContext.cs`, `WorldContext.cs` and their model snapshots.
- **A new quest no longer loses the whole character save now and then** (server, settler run 20261112-210445, character 176): the first failed save logged `InvalidOperationException: The instance of entity type 'CharacterQuestObjectiveModel' cannot be tracked because another instance with the same key value for {'Id', 'QuestId', 'Index'} is already being tracked` from `QuestObjective.Save` (Add), right after the settler accepted Emergency Extraction (4785, three objectives). The next save then failed on the `character_quest_objective` foreign key (objective rows whose quest row was in the lost save) and the 21 after it with "expected to affect 1 row(s), but actually affected 0", until logout. No quest sat in two collections: `character_quest_objective.index` had the same mapping fault as `character_path.path` (01fc448d), a key part with a default value, so EF treats it as store generated. Objective 0 (index 0 is the CLR default) is given a temporary key value on Add, and that value comes from one server-wide counter that counts down from 255 and wraps. Whenever the counter stands at 1 to N-1 while a quest with N objectives is created, objective 0 takes the key of a real objective of the same quest and that objective's Add throws. A throwaway EF test reproduced it (6 conflicts in 600 four-objective quests, at counter values 3, 2, 1). Any character can hit it, players included, about (N-1)/256 per new quest with N objectives. Only this one failure is in the logs since 11-09 (no character 1 save failures). The index is now never generated (`CharacterContext.cs` plus the model snapshot, no schema change), and `QuestManager.Save` now saves each quest on its own: a quest whose rows cannot be tracked is logged with its id and skipped, its unsaved objectives keep their changes for the next save, and the rest of the character is saved. Other composite keys with the same mapping (achievement, appearance slot, currency, zone map hex group, pet customisation type and others) were listed but not changed.
